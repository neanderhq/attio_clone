## Outcome and boundaries

Build an original, public **demo workspace** in which a rep can create a company, a linked person, and a linked deal; set the deal's pipeline stage, owner and value; then add a note and a task. A manager visiting the **same demo workspace** should see those saved changes, including after refreshing the page. This is real shared database persistence, not browser-local state, a static mock, or separate per-visitor samples.

This is a public demonstration, **not a private or production-safe CRM**. No login, permissions, tenant isolation, privacy promise, or safe storage for real customer information is included. Put a plainly visible demo-data warning near the workspace entry and forms: anyone with access may view or change shared records; use fictional data only. Do not suggest rep and manager have enforced roles: they are two visitors to the same public workspace. No Attio logos, screenshots, protected assets, or copied visual identity.

**Now:** linked Companies, People, Deals; stage/owner/value on deals; notes and tasks; searchable list and board presentations; a compact summary; detail view with relationship and pipeline context. Workspace navigation exposes People, Companies, Deals and Tasks.  
**Next, not now:** user-defined schema/attributes, saved or configurable views, imports, authentication and roles.  
**Later:** reporting, automation, AI and integrations. A small current-state summary is not the later reporting product.

## Product model and behavior to implement

Use a single shared demo workspace at first. Model **company** (name plus optional concise context), **person** (name, optional contact details, linked company), and **deal** (name, linked company and person, stage, owner, monetary value). A person's selected company must match the deal's company; validate this on the server, not only in the form. Require a company before the person/deal linked flow; support selecting existing records as well as creating them. Stable IDs and foreign keys should preserve links across refreshes. Prefer straightforward fixed fields for this phase rather than a generic attribute engine.

Use a small, explicit ordered set of pipeline stages (for example New, Qualified, Proposal, Won, Lost); define it in one place and make transitions editable in both board and detail/list contexts. Owner is a simple display label in the public demo, **not** a signed-in user or authorization boundary. Store deal value as a nonnegative integer in minor currency units with an explicitly labeled demo currency (e.g. USD); format on display rather than storing a float. Decide whether a blank value is allowed, then enforce the same rule in all entry points. No forecast or currency-conversion claim.

Notes attach to a record, with text and creation time. Tasks attach to a record, with title, due date (optional), completion state and creation time; a task can be added from detail and found in Tasks navigation. Avoid fake author attribution when there is no authentication. For a manageable first implementation, a note/task may target one company, person **or** deal via an explicit type and ID, with server-side referential checks; detail views show their own activity, not an unverified roll-up from every related record. If a roll-up is desired, specify and test that query separately.

The primary surface should include: a lightweight summary (counts, pipeline totals and due-task attention based on actual stored data); searchable lists for people, companies and deals; a board grouped by deal stage with readable stage, owner and value; details with links back to associated records and actions to change stage/add notes/tasks. Search should operate over stored records and return a truthful empty state. Board and list are two views over the **same** deals, not separate datasets. Keep results bounded/paginated if needed and avoid misleading totals when the view is partial. Database queries should be the source of truth after writes; show a saving state and refreshed result, not an optimistic success that can disappear on reload.

## Public API bounds and verification (21 Oct 2026)

`/api/crm` returns the same complete five-collection response while each collection has at most 500 records. A GET fetches at most 501 rows per table and returns a clear `409` if any collection exceeds 500; it never displays a truncated set with misleading counts. New company, person, deal, note and task writes return `409` once their collection reaches 500. The create check and insert are separate database operations, so simultaneous creates may exceed the cap; a subsequent GET then reports the overflow. This is a small public demo limit, not a durable quota or archival feature.

POST, PATCH and DELETE accept at most 16 KiB of JSON request body, including when `Content-Length` is absent; oversized bodies return `413`. Writes are limited to 60 attempts per 60 seconds per application process, including invalid attempts; excess writes return `429` and `Retry-After`. The throttle is shared by all visitors to that process, resets on restart and is not coordinated across multiple instances. Multi-instance deployment needs a shared, atomic limiter (for example a database or gateway limit) before treating this as a reliable abuse quota. No visitor identity or authentication is implied. Expected validation and limit failures return specific JSON errors; unexpected database failures return a generic `503` without connection details.

Notes and tasks use `(target_type, target_id)` with an API existence check. PostgreSQL has no foreign key for that polymorphic pair, so direct database changes and a deletion race can leave orphan activity. Repair requires a data audit and a reviewed migration with type-specific references or triggers; no migration was made in this remediation, and no unconfirmed database was migrated.
